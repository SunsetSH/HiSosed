# ADR-0001: custom integration как оркестратор существующих media_player

- Статус: принято для MVP
- Дата: 2026-09-03
- Связанные требования: HS-FR-001–055, HS-NFR-001–008

## Контекст

Нужно локально запускать случайные короткие аудиофайлы по клеточной сетке и расписанию, использовать UI Home Assistant на Android и Windows, а также позволить пользователю выбирать собственные файлы и устройства вывода.

Рассмотрены три варианта:

1. custom integration вызывает стандартные `media_player`-действия;
2. Home Assistant add-on содержит собственный audio renderer/stream server;
3. только Blueprint/automations и helpers без собственного backend.

## Решение

Для MVP выбрать вариант 1: один config entry асинхронной custom integration на Python с `integration_type: helper`, использующей Media source и `media_player.play_media`. Для редактирования сложных сценариев позже добавить TypeScript/Lit panel, но scheduler и состояние остаются в backend.

Архитектура предусматривает `MediaPlayerPort`, поэтому вариант 2 можно подключить новым адаптером после аппаратного доказательства необходимости. Автоматического скрытого fallback на внешний сервис не будет.

## Причины

- использует уже подключенные Home Assistant устройства;
- не требует привилегированного доступа к аудиодрайверам хоста;
- устанавливается через HACS и работает локально;
- Python соответствует нативной модели интеграций Home Assistant;
- стандартный Media browser уже решает загрузку и защищенную выдачу локальных файлов;
- scheduler можно покрыть детерминированными тестами независимо от UI.

Вариант с одними automations отклонен: динамическая сетка, versioned state, recovery, список weighted audio и защита от stale callback превратят YAML/Jinja в трудно тестируемую бизнес-логику.

Add-on не выбран сразу: он усложняет установку, поддерживается не во всех типах развертывания одинаково и требует отдельного жизненного цикла файлов/кодеков. Он оправдан только для gapless или проблемных плееров.

## Последствия

Положительные:

- небольшой и понятный MVP;
- один UI для Android и Windows;
- отсутствие облака и собственных учетных записей;
- совместимость с разными плеерами через общий интерфейс Home Assistant.

Отрицательные:

- точность старта зависит от сети и интеграции плеера;
- 100% активных клеток не гарантируют отсутствие акустических разрывов;
- `announce`, queue и state reporting нельзя считать одинаковыми для всех устройств;
- перед обещанием совместимости нужен hardware probe.

## Условия пересмотра

ADR пересматривается, если хотя бы одно целевое устройство:

- теряет более согласованного допустимого процента коротких команд;
- имеет неприемлемую задержку после паузы;
- не может получить локальный Media source URL;
- требует гарантированного непрерывного сигнала;
- не обеспечивает пригодную семантику replace/queue.

Тогда создается новый ADR с выбором между предварительной сборкой длинных фрагментов, локальным streaming renderer или специализированным endpoint.
