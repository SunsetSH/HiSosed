# План разработки

## 1. Рекомендуемая стратегия

Начинать следует не с красивой сетки, а с короткого вертикального прототипа на реальном целевом плеере. Если колонка надежно принимает отдельные короткие команды, MVP остается компактной custom integration. Если нет, это обнаружится до разработки UI и приведет к обоснованному решению о renderer/add-on.

Оценка для одного разработчика, знакомого с Python, но не с внутренностями Home Assistant:

- технический MVP без отдельной панели: 2–3 недели;
- удобная панель, устойчивость и HACS-релиз: еще 2–3 недели;
- потоковый/gapless renderer при необходимости: еще 2–5 недель в зависимости от кодеков и целевых установок.

Это диапазоны, а не обязательства: главный множитель — поведение конкретных медиаплееров.

## 2. Этап 0 — проверка осуществимости на оборудовании

Срок: 1–3 дня.

1. Подготовить тестовые WAV/MP3 длительностью 1, 2 и 5 секунд и загрузить их в `/media/hi_sosed`.
2. В Home Assistant Developer tools вручную вызвать `media_player.play_media` для целевого устройства.
3. Измерить задержку старта при серии команд и после пауз 5, 15 и 30 секунд.
4. Проверить локальный Media source URI, прямой URL, `announce`, `enqueue` и замену текущего клипа.
5. Проверить состояние плеера и поведение при недоступности сети.
6. Зафиксировать матрицу результатов в отдельной ADR только если нужен renderer/add-on.

**Ворота решения:**

- команды надежны и задержка приемлема → orchestration MVP;
- короткие клипы теряются, но очередь надежна → исследовать предзаполнение очереди;
- слышимые разрывы недопустимы или команды теряются → длинные предварительно собранные фрагменты/локальный поток.

## 3. Этап 1 — каркас интеграции

Срок: 1–2 дня.

- создать репозиторную структуру custom integration;
- добавить `manifest.json` с уникальным domain, `version`, `config_flow` и типом интеграции;
- указать `integration_type: helper` и `single_config_entry`, поскольку сценарии живут внутри одного локального runtime;
- реализовать setup/unload одного config entry;
- добавить `translations/en.json` и `translations/ru.json` (для custom integration нельзя полагаться только на core `strings.json`);
- настроить pytest, Ruff, typing, Hassfest и HACS validation;
- добавить минимальный config flow и тесты установки/повторной установки/удаления.

Результат: пустая интеграция устанавливается и корректно выгружается.

## 4. Этап 2 — чистое доменное ядро

Срок: 2–4 дня.

- типы `Scenario`, `ScheduleWindow`, `GridSpec`, `AudioItem`, `RuntimeCheckpoint`;
- валидация диапазонов и инвариантов;
- точная генерация активных позиций;
- взвешенный выбор аудио;
- вычисление окна через полночь и следующей клетки;
- семантика ревизий, поколений и переходов состояний;
- property-based или параметризованные тесты граничных значений.

Результат: алгоритм полностью работает без запущенного Home Assistant.

## 5. Этап 3 — минимальный вертикальный playback slice

Срок: 2–4 дня.

- адаптер стандартного `media_player.play_media`;
- действия `start` и `stop`;
- scheduler на абсолютных deadline;
- один жестко заданный в тестовой конфигурации сценарий;
- тест гонки stop/callback, недоступного плеера и ошибки service call;
- ручная проверка на целевой колонке.

Результат: сценарий реально воспроизводит случайные локальные файлы и гарантированно прекращает новые команды.

## 6. Этап 4 — хранение и полноценное расписание

Срок: 3–5 дней.

- versioned `Store`, миграция schema v1 и atomic save;
- CRUD сценариев через application service;
- дни недели, окна через полночь, timezone/DST;
- восстановление после restart и пропуск missed cells;
- optimistic revision и сериализация мутаций;
- `regenerate` и `preview`;
- Repair issue для невосстановимой конфигурации.

Результат: backend соответствует требованиям по сохранности и расписанию.

## 7. Этап 5 — нативные сущности и базовый UI

Срок: 2–4 дня.

- switch включения расписания;
- sensor состояния и следующего события;
- отключенный по умолчанию диагностический sensor;
- многошаговый config/options flow для основных параметров;
- selector целей `media_player` и Media source;
- переводы, сообщения ошибок и accessibility-проверка стандартных форм.

Результат: продукт можно настроить без YAML и без кастомной панели, пусть управление списком файлов пока менее удобно.

## 8. Этап 6 — панель сетки

Срок: 5–8 дней.

- зарегистрировать локальный frontend resource/panel;
- авторизованные WebSocket CRUD-команды и подписку runtime state;
- экран списка сценариев;
- редактор расписания, плотности, размера цикла, targets и weighted audio list;
- визуализация клеток с текстовыми/ARIA-состояниями;
- optimistic concurrency conflict UI;
- адаптивные раскладки для узкого Android и Windows desktop;
- компонентные тесты и e2e основных потоков.

Результат: UX соответствует описанию «поле из клеток».

## 9. Этап 7 — hardening и выпуск

Срок: 3–5 дней.

- сценарии reload/update/remove, restart и corrupted store;
- ошибки/таймауты нескольких плееров;
- нагрузочный тест длинного окна с короткими клетками;
- privacy-review логов и diagnostics;
- пользовательская инструкция по `/media`, Container volumes и совместимости плееров;
- семантическая версия, changelog, `hacs.json`, GitHub release;
- установка чистого релиза через HACS и ручное обновление предыдущей версии.

## 10. Последовательность функций по релизам

### v0.1.0 — рабочий MVP

- один config entry;
- несколько сценариев;
- local Media source;
- start/end/weekdays;
- сетка, плотность, weighted random;
- один или несколько targets;
- start/stop/regenerate/preview;
- switch/sensor;
- restart recovery;
- стандартные UI flows.

### v0.2.0 — удобство

- кастомная панель и живая сетка;
- пресеты плотности;
- массовое включение/отключение файлов;
- импорт/экспорт только конфигурации сценариев без медиа;
- диагностический отчет без приватных данных.
- опциональный лицензированный стартовый sound pack через собственный Media source.

### v0.3.0 — совместимость плееров

- экспериментальные overlap policies;
- capability probe и предупреждения;
- профили устройств;
- renderer/add-on только если собраны воспроизводимые данные о разрывах.

## 11. Definition of Done для каждой вертикальной задачи

Задача завершена, когда:

1. связанным требованиям присвоены тесты;
2. проверены success, cancel/unload, retry/error и stale completion, если применимо;
3. нет блокирующего I/O в event loop;
4. строки локализованы, UI доступен с клавиатуры;
5. логи не содержат имен/путей пользователя;
6. выполнены targeted tests, затем полный suite, lint, format и validators;
7. результат вручную проверен на поддерживаемом Home Assistant;
8. известные аппаратные ограничения записаны, а не скрыты автоматическим fallback.
