# План тестирования

## 1. Цель

Доказать не только распределение случайных клеток, но и более важное свойство: после окончания окна, остановки, изменения или выгрузки интеграции не возникает запоздалого воспроизведения.

## 2. Модульные тесты домена

### Сетка

- `N = 1`, плотности 0%, 49%, 50%, 100%; проверить выбранное правило half-up;
- разные `N` и плотности: число флагов всегда равно рассчитанному;
- нет повторяющихся индексов;
- при одном seed результат стабилен;
- при смене seed распределение может меняться, но инварианты сохраняются;
- попытка избежать полного повтора не зависает при 0%, 100% и единственно возможном паттерне;
- неизвестная версия алгоритма отклоняется, а не интерпретируется как текущая.

### Выбор аудио

- отключенные и нулевые веса никогда не выбираются;
- один доступный файл выбирается всегда;
- пустой набор отклоняется до запуска;
- детерминированная последовательность на test seed;
- статистический smoke-test весов с широким допуском, без flaky точного процента.

### Время

- обычное дневное окно;
- окно через полночь;
- невыбранный день;
- ровно начало и ровно конец окна;
- restart между клетками;
- callback опоздал на одну и много клеток;
- весенний пропуск и осенний повтор часа в timezone с DST;
- изменение timezone;
- `start == end` отклоняется.

## 3. Тесты scheduler и гонок

Использовать управляемые часы и fake event helper, не реальные `sleep`.

- start создает ровно один callback;
- повторный start идемпотентен;
- stop сначала меняет generation, затем отменяет callback;
- callback, уже вошедший в обработчик до stop, повторно проверяет generation перед side effect;
- изменение revision делает старый callback неактуальным;
- regenerate не дублирует scheduler;
- unload отменяет все callbacks и listener;
- старая async service completion не меняет состояние нового поколения;
- конец окна между resolve media и play предотвращает play;
- ошибка одного target не отменяет вызов другого;
- timeout не запускает немедленный retry storm;
- медленный callback не создает накопительный временной дрейф.

## 4. Тесты хранения

- первый запуск без Store;
- сохранение/загрузка schema v1;
- миграция каждой опубликованной старой версии;
- неизвестная будущая версия;
- обрезанный JSON и неверные типы;
- ошибка записи/мало места оставляет предыдущую конфигурацию пригодной;
- optimistic revision conflict;
- checkpoint на начале, смене цикла и остановке;
- restart внутри/вне окна;
- отсутствующий audio URI при восстановлении не вызывает playback.

## 5. Интеграционные тесты Home Assistant

- config flow success, duplicate и abort;
- options/reconfigure update без двойной reload-гонки;
- setup, unload, reload, remove config entry;
- регистрация действий один раз независимо от числа entries;
- валидация схем каждого действия;
- права WebSocket: admin write, authenticated read, unauthorized reject;
- setup/unload switch и sensor platforms;
- translated entity names и ошибки для `ru`/`en`;
- mock `media_player.play_media` получает правильный target, URI и content type;
- сущность `unavailable`, service error и удаленный entity target;
- Recorder не получает обновление на каждую клетку.

## 6. Контрактные тесты панели

- создание и редактирование сценария;
- конфликт revision показывает понятное сообщение и не затирает данные;
- сетка различает прошедшие/текущую/активные/тихие клетки текстом и цветом;
- полная работа с клавиатуры;
- 200% zoom и узкий Android viewport;
- reconnect WebSocket повторно получает snapshot, не создает вторую подписку;
- stop доступен при частичной ошибке загрузки редактора;
- backend остается источником истины после refresh страницы.

## 7. Аппаратная матрица

Для каждого реально поддерживаемого типа `media_player` записать:

| Проверка | Результат |
|---|---|
| URI из `/media` доступен устройству | pass/fail |
| MP3/WAV/другие нужные форматы | список |
| Старт после 5/15/30 секунд тишины | задержка и потери |
| Серия клипов по 1/2/5 секунд | процент успешных запусков |
| Поведение `replace` | прерывает/игнорирует/очередь |
| Поддержка `announce` и восстановление | да/нет/частично |
| Достоверность `playing/idle` | да/нет |
| Потеря сети и восстановление | наблюдение |

Минимум для релиза: целевой пользовательский плеер и один программный mock с управляемыми ошибками. Для заявления широкой совместимости нужны проверки Cast, Sonos/аналогичного сетевого плеера и хотя бы одного Bluetooth-моста.

## 8. Нагрузочные и recovery-тесты

- 24 виртуальных часа с клеткой 1 секунда без утечки callbacks/tasks;
- 20 сценариев, из которых 5 одновременно активны;
- 10 targets с частичными ошибками;
- 1000 audio items в редакторе и Store;
- restart на каждой критической фазе: до checkpoint, после checkpoint, во время resolve, до play, после play;
- low storage при сохранении;
- повреждение временного/основного storage файла;
- обновление версии интеграции с активным сценарием.

## 9. Команды quality gate

Точные команды зависят от выбранного шаблона репозитория и фиксируются при scaffold. Ожидаемый набор:

```text
pytest <targeted tests>
pytest
ruff check .
ruff format --check .
mypy custom_components/hi_sosed
python -m script.hassfest   # в подходящей dev-среде Home Assistant
HACS validation GitHub Action
frontend unit/e2e tests
```

Нельзя заявлять прохождение Android/Windows или реального плеера по результату одних mock-тестов.
